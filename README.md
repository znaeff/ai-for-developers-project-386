# Календарь звонков

Учебное приложение от Hexlet для бронирования встреч

## Роли

- Владелец — администратор календаря, его функции доступны без регистарции по заранее определённому URL-у, он создаёт типы встреч с описанием и длительностью, может смотреть встречи, соданные гостями.
- Гость — пользователь календаря, его функции доступны без регистарции, он бронирует (регистрирует, создаёт) встречи с типом, созданным администратором в свободные слоты времени.


## Сценарий работы для создания встречи
- Владелец видит список типов встреч.
- Владелец при отстуствии нужного типа создаёт его с описанием и длительностью.
- Гость видит список типов встреч.
- Гость выбирает нужный тип встречи.
- Гость видит календарь со свободными слотами на следующие 14 дней, считая от текущего времени.
- Гость выбирает нужный слот и бронирует встречу выбранного типа со своими именем и почтой.
- Слоты, которые заняла встреча, больше не доступны для бронирования.

## Расписание и слоты

Владелец работает по будням, с понедельника по пятницу, с 09:00 до 18:00 по поясу `Europe/Moscow` (UTC+03:00, без перехода на летнее время). Выходные исключены.

- Кандидаты на начало слота идут каждые 30 минут, начиная с 09:00.
- Встреча длительностью `durationMinutes` должна целиком помещаться до 18:00: подходят только старты, для которых `start + durationMinutes <= 18:00`.
- Длительность не обязана быть кратной 30 минутам. Сетка стартов остаётся 30-минутной: для 45-минутной встречи старт в 09:00 заканчивается в 09:45, а следующие кандидаты — 09:30, 10:00 и так далее.
- Показываются только будущие слоты (`start > сейчас`) в окне до 14 дней (`start < сейчас + 14 дней`).
- Занятые Брони скрывают свои слоты: если встреча 09:00–09:45 уже забронирована, слоты 09:00 и 09:30 не предлагаются. Занятость учитывается в рамках выбранного Типа встречи.

## Стек

- **Монорепозиторий:** pnpm workspaces (`apps/backend`, `apps/frontend`), версии инструментов управляются через [mise](https://mise.jdx.dev/) (Node.js 22 и pnpm указаны в `mise.toml`).
- **Бэкенд:** TypeScript + Node.js 22, встроенный модуль `node:http`. Метод `GET /reserve` возвращает текст `Reserved`; в контейнере сервер также раздаёт собранный фронтенд и понимает префикс `/api`.
- **Фронтенд:** TypeScript, Vite, React, shadcn/ui на базе Tailwind CSS v4. Стартовая страница со ссылками на страницы гостя и владельца, навигация без роутера. На `/owner` Владелец создаёт Типы встреч, видит их список и список всех Броней с кнопкой «Обновить»; на `/guest` Гость выбирает Тип встречи, видит свободные Слоты, сгруппированные по дням, затем выбирает Слот, вводит имя и почту и получает подтверждение Брони.
- **Docker:** multi-stage образ на Node 22; один контейнер отдаёт интерфейс и API на одном порту (`PORT`, по умолчанию `3000`).
- **Тесты:** ESLint (линтер), `tsc --noEmit` (проверка типов), Vitest (HTTP-тесты бэкенда), Playwright (end-to-end тесты фронтенда). Линтер, типы и юнит-тесты объединяет `mise run check`; e2e запускаются отдельно через `mise run test:e2e`.

## Установка

```bash
mise install   # установить Node.js 22 и pnpm из mise.toml
pnpm install   # установить зависимости всех пакетов монорепозитория
```

## Docker

Образ содержит собранные бэкенд и фронтенд; для запуска контейнера не нужны локальные Node.js и pnpm.

```bash
mise run docker:build   # собрать образ calendar-booking:local
mise run docker:run     # запустить контейнер на http://localhost:3000
```

Порт внутри контейнера задаётся переменной `PORT`. Например, на 8080:

```bash
docker run --rm -e PORT=8080 -p 8080:8080 calendar-booking:local
```

В CI отдельный workflow `.github/workflows/docker.yml` собирает образ, поднимает контейнер и проверяет `/` и `/api/reserve`.

## Тесты

```bash
mise run check
```

Одна команда последовательно запускает линтер (`pnpm lint`), проверку типов (`pnpm typecheck`) и тесты бэкенда (`pnpm test`). Эти же проверки выполняются в GitHub Actions на каждый пуш и pull request (workflow `.github/workflows/ci.yml`). HTTP-тесты сами поднимают бэкенд на свободном порту, создают Типы встреч и Брони через API и закрывают сервер; запускать бэкенд отдельно не нужно.

End-to-end тесты фронтенда запускаются отдельно:

```bash
mise run test:e2e
```

Playwright сам поднимает бэкенд на 3000 и Vite на 5173 и проверяет реальные страницы; в CI это делает workflow `.github/workflows/playwright.yml`.

## Использование

```bash
mise run dev:backend    # бэкенд: http://localhost:3000/reserve
mise run dev:frontend   # фронтенд: http://localhost:5173
```

Можно запустить оба процесса одной командой: `mise run dev`. Откройте http://localhost:5173 — на стартовой странице «Календарь звонков» две ссылки: «Бронировать встречу» (`/guest`) и «Управление календарём» (`/owner`). На странице владельца доступна форма создания Типа встречи, список уже созданных Типов встреч и список всех Броней с датой и временем по Москве, именем и почтой Гостя; кнопка «Обновить» перезагружает список Броней. На странице гостя Гость видит список Типов встреч, выбирает нужный, получает свободные Слоты по дням, выбирает Слот, вводит имя и почту и получает подтверждение Брони; занятый Слот исчезает из списка. Вернуться к списку Типов встреч можно кнопкой «Выбрать другой тип». С обеих страниц можно вернуться «На главную».

## API

Типы встреч и Брони хранятся в памяти процесса и сбрасываются при его рестарте.

- `GET /meeting-types` — список Типов встреч.
- `POST /meeting-types` — создание Типа встречи. Тело запроса: `{ "title": "…", "description": "…", "durationMinutes": 30 }`. Успех — `201` с созданным Типом встречи, невалидные данные — `400` с телом `{ "error": "…" }`.
- `GET /meeting-types/:id/slots` — свободные Слоты выбранного Типа встречи на ближайшие 14 дней. Ответ — массив `{ "startsAt": "2026-01-05T09:00:00+03:00", "endsAt": "2026-01-05T09:30:00+03:00" }`; даты в ISO 8601 с московским смещением `+03:00`. Слоты вычисляются из расписания и длительности; Слоты, занятые Бронями этого Типа и пересекающиеся с ними, не возвращаются. Для неизвестного `id` — `404` с телом `{ "error": "…" }`.
- `GET /bookings` — список всех Броней, отсортированный по времени начала (`startsAt`). Ответ — массив записей `{ "id": "…", "meetingTypeId": "…", "meetingTypeTitle": "Консультация", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com", "createdAt": "2026-01-05T05:12:34.000Z" }`. Если Броней нет, возвращается `[]`.
- `POST /bookings` — создание Брони. Тело запроса: `{ "meetingTypeId": "…", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com" }`. `meetingTypeId` и `startsAt` обязательны, `startsAt` должен совпадать с одним из свободных Слотов выбранного Типа. Успех — `201` с Бронью `{ "id": "…", "meetingTypeId": "…", "startsAt": "2026-01-05T09:00:00+03:00", "guestName": "Анна", "guestEmail": "anna@example.com", "createdAt": "2026-01-05T05:12:34.000Z" }`. Ошибки возвращаются с телом `{ "error": "…" }`: `400` — пустое имя, некорректная почта, отсутствующие или некорректные `meetingTypeId`/`startsAt` (включая время вне доступных Слотов); `404` — неизвестный Тип встречи; `409` — Слот уже занят. Проверка занятости и запись Брони выполняются атомарно в рамках одного процесса.

В dev-режиме Vite проксирует `/api/*` на бэкенд и снимает префикс `/api`; в production тот же префикс обрабатывает `createServer()`.

Бэкенд по-прежнему отвечает на `GET /reserve` текстом `Reserved`; кнопка `Check` с главной убрана. Запрос к `/api/reserve` всё ещё проксируется Vite на `http://localhost:3000/reserve`.

Для production-сборки выполните `pnpm build`; собранный бэкенд запускается командой `pnpm --filter @app/backend start` (порт задаётся переменной `PORT`, по умолчанию `3000`). Готовый способ собрать и запустить приложение — `mise run docker:build` и `mise run docker:run`.
